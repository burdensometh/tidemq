# TideMQ v1 二进制契约

所有整数均为大端。名称字段为 `bytes` 形式的 UTF-8，标识符限制为 1–64 个 ASCII 字符，首字符为字母或数字，余下还允许 `_` 和 `-`。`bytes` 是 `i32 length` 和对应长度的原始字节。集合为 `i32 count` 再按下文顺序重复元素。偏移、水位、时间戳及序号使用 `i64`。分区引用记为 `partition = topic, i32 number`。

## TCP

帧由 `i32 length, i64 request_id, u8 opcode, body` 组成。`length` 包括请求 ID、操作码和正文。ID 在每条 TCP 连接内从正整数递增。连接开始时最大允许 1024 字节长度。HELLO 完成后使用协商上限。成功响应沿用请求 ID，操作码为请求操作码按位或 `0x80`。错误响应操作码为 `0x7f`，正文为 `i32 code, text details`。

以下表中的方括号表示带计数的集合。空正文的长度为 0。

| 操作码 | 请求 | 成功响应 |
| --- | --- | --- |
| 1 HELLO | `i32 min_version, i32 max_version, i32 requested_frame_bytes` | `i32 version, i32 frame_bytes, i32 max_batch` |
| 2 PING | 空 | 空 |
| 3 PRODUCE | `producer, i64 sequence, topic, i32 partition_or_minus_one, bytes key, bytes payload` | `producer, i64 sequence, partition, i64 offset, i64 append_ms, u8 replayed` |
| 4 JOIN | `group, member, [topics]` | `group, member, i64 epoch, [partition]` |
| 5 ASSIGN | 空 | 和 JOIN 响应一致 |
| 6 PULL | `i64 epoch, i32 limit` | `[lease]` |
| 7 ACCEPT | `i64 epoch, [ref]` | `[(ref, i64 expiration_ms)]` |
| 8 ACK | `i64 epoch, [ref]` | `[(partition, i64 next)]` |
| 9 LEAVE | 空 | 空 |
| 10 TOPICS | 空 | `[(topic, i32 partitions)]` |
| 11 PARTITION | `partition, i32 recent_limit` | `partition, i64 retained_from, i64 end, i32 total_segments, [(i64 base, i64 end, i64 bytes, i64 created_ms, i64 last_append_ms, u8 active)]` |
| 12 GROUP | `group` | `group, i64 epoch, [topics], [(member, [partition])], [(partition, i64 next, i32 ahead, i32 retrying)]` |
| 13 DEAD_LETTERS | `group, i64 start_sequence, i32 limit` | `i64 cursor, [dead_letter]` |
| 14 RETIRE | 空 | `i32 deleted_segments` |
| 15 RETENTION_PREVIEW | `partition` | `partition, i64 evaluated_ms, i64 min_age_ms, i64 allowed_end, i32 limiting_group_count, [group], i32 eligible_segments, i64 eligible_bytes, i64 resulting_low, i64 kept_base, i64 kept_end, u8 active, u8 above_frontier, i64 remaining_age_ms` |
| 16 FLOW | `group` | `group, i64 epoch, i64 observed_ms, i32 window, i32 max_inflight_per_member, i32 members, i32 reserved, i32 accepted, [(member, i32 assigned_partitions, i32 reserved, i32 accepted, i64 earliest_deadline_ms)]` |

`message = i64 offset, i64 append_ms, producer, i64 producer_sequence, bytes key, bytes payload`。消息的分区由所在帧字段或文件路径指定。

`lease = i64 id, i64 epoch, i64 reservation_deadline_ms, i32 next_attempt, partition, message`。

`ref = i64 id, partition, i64 offset`。

`dead_letter = i64 sequence, group, i32 attempts, i64 terminal_ms, partition, message`。

布尔值为单字节 0 或 1。合法请求遇到业务拒绝时连接仍可继续。非法长度、截断或接收超时会结束连接。首帧必须协商版本。协议支持一个 TCP 连接加入一个成员会话，生产和监控请求也可以使用该连接。客户端需读取完整的 PULL 成功帧后发送 ACCEPT，并在处理完成后发送 ACK。ACCEPT 对同一活跃租约重复调用时返回原期限，尝试次数保持不变。成员代在 JOIN、LEAVE 及同名替换时推进；发生转移的分区进入协作交接，旧成员会话结束（优雅 LEAVE 交回或断线、同名会话被替换）前新成员 PULL 不到该分区，只有旧会话能结算已有投递。用 ASSIGN 取得当前代后可跨代结算同一会话的租约；交接期内沿用租约旧代确认转移分区的批次也有效。其余跨代接受或确认返回 `STALE_EPOCH`，跨会话租约返回 `UNKNOWN_LEASE`。

自动路由使用 Java `Arrays.hashCode(byte[])`，从 1 开始按 `hash = 31 × hash + signed_byte` 吸收每个字节，32 位溢出按二进制补码处理。对结果取分区数的非负模。FLOW 是当前租约账本的观察值。到期条目在维护或下一次相关投递操作时清扫。成员样本按名称排序，无活跃租约时最早期限为 -1。

## 磁盘

`segments/topology.v1` 用 UTF-8 保存固定话题拓扑。每个分区由 `segments/<topic>/<partition>/<base>.seg` 下的连续段组成，段名中的十进制基偏移补齐 20 位。只有基偏移最大的段可以追加。段启动时用实际记录的文件位置重建索引。

段和追加日志都使用 `magic:i32, version:i32=1, base:i64, created_ms:i64` 的 24 字节头。其后是 `body_length:i32, body, crc32c:i32` 连续记录，CRC32C 只覆盖正文。

| 文件 | Magic | 单条正文 |
| --- | --- | --- |
| `*.seg` | TMSG | `message` |
| `produce.v1.journal` | TMPR | `producer, i64 sequence, partition, i64 offset, i64 append_ms, 32-byte SHA-256` |
| `deadletter.v1.journal` | TMDL | `dead_letter` |

生产摘要输入是 `partition, bytes key, raw payload`。三个文件类型的内容都以真实写入为准。活跃追加日志只可截去最后一个物理长度不足的记录。封口段的截断、完整记录 CRC 不匹配或偏移洞都会使启动失败。

组快照 `groups/<group>.group` 外层是 `TMGP, i32 version=1, bytes body, crc32c:i32`。正文由 `group, i64 epoch, [topics], [(partition, i64 next, [i64 completed_ahead], [(i64 offset, i32 attempts)])]` 构成。替换前先 force 同目录临时文件，原子替换后再 force 父目录。组成员、分配和实际活跃租约是 TCP 进程状态，重启后由新的 JOIN 建立会话和更高的组代。

## 持久化边界

1. 生产操作先强制落盘消息段，再强制落盘生产回执，最后回复。若段完整但回执缺失，启动时从保留消息重建。保留扫描只能在当前生产操作离开提交区后运行。
2. 接受或确认会提交组快照。若请求在可观测回复前中断，应用层可结合回执、水位和之后的投递判断结果。出现模糊的生产结果时重发原始身份和消息。
3. 终止一次已接受的最后尝试先写入独立死信日志，再关闭原组偏移。重启先从已有死信回执修补缺失的组快照更新，再处理没有活跃租约的耗尽条目。
4. 回收从最老封口段开始，物理删除后强制同步父目录。多个订阅组中的最小连续水位决定可见下界。

`Boundary` 提供段 force 前后、帧回复前、成员代替换前后和死信 force 前后的进程内回调。测试传入可控的 `Clock`，用正常 TCP 请求触发指定边界。force 前掉电可能留下零、部分或完整记录，只有客户端成功生产回执对应的段和回执已完成持久化。
